## 四、五条反直觉共识（含反对派）

### 1️⃣ 子代理**只该用来"读"，不该用来"写"**
> `mci77777`：「subagent 只能用于探索。写代码还是让 main agent 做——特别是现在 gpt-6.1 这么便宜、claude-opus-5-5 缓存免费的情况。claude 的 subagent 会**全量重建缓存，显著减少缓存命中率**，且丢失重要的需求思维，导致写代码只写他负责的那一小步，**局部没问题，全局思维就差了**。」

> `XTer` 总结子代理三大正当用途：**explore（省钱、防上下文腐坏）、review（独立上下文）、frontend（拯救 gpt 的前端）**

### 2️⃣ 极致反方：**别迷恋 subagent**
帖子 `[2983485] 别迷恋subagent。返工潮+屎山堆叠神器`（1190 浏览）评论区：

> `ihalo`：「附议，subagent 写的代码不堪入目」
> `light2199`：「它不会只改自己负责的部分，先给你拉一堆 MCP，再激活一堆 skill，再去探索一波，然后再写一堆乱七八糟的，然后主线程还喜欢边等边改，要么改一半主线程停了说自己来。」
> `yeahhe`：「我经常把 Inline execution 写到长期记忆里。除非特别简单的任务，否则我**宁愿手动压缩、自动压缩，也不用 Subagent**。」
> `NepElder`：「已经半年没用过 subagent 功能了，感觉良好。」

**但反方内部也给了路径**——`alaha` 把子代理分成两类，值得抄：

| 类型 | 代表 | 机制 | 现阶评价 |
|---|---|---|---|
| **sync（同步）** | opencode 型 | 主代理最后一次 tool call 一次性派出 N 个，等全部回来再继续 | ✅ 除了浪费点时间，基本不会出大问题 |
| **async（异步）** | codex / hermes 型 | 主代理与子代理同时跑，通过通信工具查询/终止 | ⚠️ "**需要旗舰模型**，连 5.6 sol 都有点糖" |

### 3️⃣ AGENTS.md 正在"由厚变薄"，甚至有人**清空后智商上升**
> `[2890697] 我把 codex 的 agent.md 清空后，似乎 gpt 智商变高了`（1024 浏览）：
> 「清空之后，gpt 不仅智商变高了，也没那么啰嗦了。」

标杆评论 `a2368883029`：
> 「**把 LLM 当 State Machine 用的提示词是效率最低的**，还容易让 Agent 左右脑互搏。」

主流收敛的新共识（`[2907147] 征求下各位的 agent.md`）：
- `asdf8249`：「拿来当**索引**用，最多加点规范，**十几行左右就够了**，其他信息拆分成多个子目录的 AGENTS.md，让模型自己去读」
- `zzzdajb`：「本质上是只适合当**导航**，只能放非常底层的原则，而不是什么都往里面塞」
- `lq36821`：只留**操作习惯向**的——自动建目录、自动建 Git 仓库、关键节点提交、轮次结束记开发日志、删文件先丢回收站
- `libook`：全局基本不写了，但**项目级的用得越来越重**（如 SDD 开发流程声明）

### 4️⃣ "弱 AI 调用强 AI"被全网群嘲，正确姿势是反过来
帖 `[3005036] 用弱AI调用强AI`（922 浏览）评论区几乎一边倒：

## 五、2026 新宠：会话编排（multi-session）

这是 2026 下半年最明显的方向转移——**从"子代理"转向"多会话"**：

| 项目 | 一句话 |
|---|---|
| **PI-Desktop** | 「多会话编排」做成插件——一个 session 指挥多个 session；官方举例：让 AI 组织辩论赛，一个 session 主持，再创正方/反方 session，最后收集观点（1723 浏览 / 27 回复） |
| **NekoCodeDesktop** | 基于 PI 内核，内置 Fusion 模式：**Lead 模型负责规划与审查、Sidekick 负责实现与验证**；支持 ACP 并行启动多个 CLI |
| **PI-Wm Desktop** | 手机远程访问 + 自定义壁纸 + **长任务上下文压缩** |
| **ccpane** | 最早一批多 agent 分屏编排（2026-02 立项），Claude Code / Codex / OpenCode 同屏并行派工 |
| **Claude Code Message (CCM)** | 跨机器 CC 会话"群聊"，纯 Python 标准库，走 SSH，**不开公网端口** |
| **Grok Build Desktop** | 多会话 + worktree + 子智能体并行 |

> 核心洞见来自 `persecute3851`：「**开 2 个对话让 sol 指挥 luna**，比在一个对话里切子代理省得多」——多会话的本质是**保住了各自的缓存前缀**。

## 六、长程任务 / 防漂移阵营

长任务（24h 挂机、无人值守）是 2026 的硬需求，催生了一批"控制层"工具：

| 工具 | 定位（原话） |
|---|---|
| **Northline**（Codex 插件） | 「位于 **Root Agent、执行运行时和 Git 仓库之间的控制层**：用持久化任务主线、版本化委派契约、结构化交接凭证和确定性验证门禁，减少长程软件开发中的**目标漂移、范围越界、过期状态和无证据完成声明**」 |
| **Long Live the Claude** | 面向 24h 长程：5 小时额度**优雅暂停 + 提示缓存保温**，「额度快耗尽时让模型自己找个合适位置停下来，额度恢复后再自己醒过来继续干」 |
| **op-lead-with-us**（agy 插件） | **opus 规划，gemini 3.8 flash 干活**，全在 antigravity 一个 app 内完成 |

**社区对"漂移"的标准解法**（`[2979536] 深度调研` 热评 `refalogy`）：
> 「最好让主 agent 把大任务拆成子任务，**一个 subagent 一次只完成一个明确的子任务**，不要让 subagent 一直自由发挥，这样就不容易漂移。」

## 七、可抄的 AGENTS.md 骨架（原话摘录）

来自 `[2894461] 耗费3亿token 让Astra总结我过往项目给出的codex子代理编排方案`——这是本次挖到**信息密度最高**的一段，直接摘录：

```markdown
## 子代理

- 简单任务主代理直接完成。只有存在可独立交付的子任务，**且并行能减少等待或隔离大量探索上下文时才派发**；
  不为了用满角色或并发额度而派发。
- 默认同时使用 **1–3 个子代理**；超过时先判断独立性、工具是否共享状态和整合成本，并受实际工具上限约束。
- 按当前工具实际暴露的角色选择 agent_type：
  - `quick_scan`  做明确的事实抽取
  - `default`     做一般证据整理
  - `code_explorer` 做复杂调用链分析
  - `reviewer`    做独立风险审查
  - `verifier`    做指定范围的验证
  - `mechanical_editor` 做明确授权的机械修改
- 主代理负责设计、复杂实现、范围决策与最终整合。
  子代理**不自行扩展范围，不派生、调用或请求新的子代理**。
- 默认 `fork_turns="none"`，传入目标、路径、已知事实、限制和完成条件；
  独立审查**不传入主代理的预设结论**。
- 任务说明必须**自包含**；已有代理适合后续同类问题时优先复用。
  不要让多个代理重复检索同一问题。
- 默认只读。机械修改必须明确文件所有权、转换规则、排除范围与验收方法。
- 通常只回传最终的结论、证据和限制；阻塞、重大反证应及时发送，不用固定进度心跳。
- 派发后先做独立工作；只有下一步确实依赖未完成结果时才等待。
  超时后检查仍需等待、缩小任务或接手，避免机械循环。
```

配套的铁律（`KallkaGo` / 社区共识）：
- **不能开多个子代理修改同一份文件**（避免并发写冲突）
- 遇到设计决策**立即交回主代理**
- 上下文超 1M 时，**拆成 2 个 main agent，而不是一个 session 走完**（`mci77777`）

## 八、低代码平台派：被工程派明确劝退

来自 `[2997377] 如何在传统业务代码中优雅的增加AI能力`（Java B 端系统，运营资料审核）：

> 「目前第一版使用 **Dify** 做的工作流编排，但是遇到问题：
> - 复杂的审核使用 Dify 做比较吃力，需要设计人员**面面俱到导致 Dify 的节点非常多，非常难维护**；
> - 如果做得比较简单，效果又不好；
> - **Dify 没有对应的 CLI/MCP**，导致 AI 没办法直接去调试 Dify，需要一定的人工介入；
> - 各业务系统接入 Dify 需要考虑鉴权、重试、容错，需要有个中台承接？
>
> **最核心的一点：很多调试很长时间的工作流，不如直接将资料发给本地 claude code 做审核，由它自由发挥效果好。**」

企业级自部署方向只有零星声音，如 `[3005347] 群策-AgenTeam`（Apache-2.0，私有化部署、用户独立沙箱、后续接低代码工作流，接企微/飞书机器人）。
